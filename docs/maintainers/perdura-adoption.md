# Perdura as a consumer

This is the downstream adoption boundary, not evidence that Perdura is already
adopted. Use the same reviewed engine, standard Skill and local adoption utility
as another existing repository. Product-specific code and policies stay there.

## Prepare the downstream change

Inspect the current downstream tree and policies. Retain its application runner,
test-gates manifest, dependence and contract-family selector, static authorities,
preparation, language tools and lockfiles. Prepare merged protocol bindings with
those exact inputs. Do not nest its complete gate inside another complete gate.
Use the structured selection provider for its existing selection algorithm;
without that provider the safe initial binding is full member validation.

Generate the ordinary adoption preview. Review runtime replacements, launcher,
policy and delivery target. Preserve existing commands until their replacements
are verified; installation alone does not make the new protocol authoritative.
The downstream owner approves and lands this change through its current process.

## Verify before retiring tools

Compare old and proposed selection on fixed source cases: new files, modified
tests, dependency changes, dynamic imports and unknown paths. Explain every
difference. Test normal failure and fresh ordinary success through the same
runner. Verify named admission, static conflict continuation and complete final
against an exact frozen source. Delivery remains separately authorized.

Have an agent organize current historical decisions into clause proposals with
original sources and rationale. Review semantic mappings; do not parse the old
working-set table or treat a few mapped rows as whole-document migration.
Retire a source's current authority only after all standing rules are accounted
for. Keep its immutable history for explanation.

Complete a real development task through the installed Skill and local tools.
Record exact commands, the source checked, human intervention points and any
friction. Only then remove replaced execution, retry, receipt and journal writers
from the downstream active path. Preserve product-specific algorithms behind
their declared adapter. Do not keep two copies that require the same future fix.

## Reusable lessons and optional optimization

Deterministic overlap, resource identity, cancellation ordering, bounded deadlines
and first-failure diagnosis are conditional Skill guidance. CPU/memory allocation
and owned-process settlement are already common execution mechanisms. The generic
scanner skips unreadable unrelated metadata while retaining failure for an owned
process it cannot settle; native owner tokens, birth identity and scratch checks
supply its ownership proof. These mechanisms differ from downstream scanning;
compare behavior rather than replacing them by name.

Adopt duration-weighted scheduling or verified CI slicing only after measuring
current contention and tail time. Preserve the test set, prove exact partition
coverage, and keep weight hints separate from passing criteria. RAM scratch and
background cleanup are not default requirements. Do not describe these optional
capabilities as implemented by the present adoption path.

Feedback flows both ways: downstream failures inform generic repairs, and a later
reviewed engine revision supplies downstream improvements. Adoption is local and
version-bound; there is no automatic update or cross-machine service.
